1. “What kind of thing is this file?” is answered five times

STRONG

Files: server/src/filemill/columns.py:94–171 · server/src/filemill/api.py:90–104,177 · server/src/filemill/preview.py:13–51 · ui/core/render.js (EDIT_RE) · ui/core/jsonl.js + adapters

Problem

The file-kind decision — folder vs link vs virtual-filesystem vs previewable vs editable — is re-derived from the filename at every seam crossing, in two languages, and the copies already disagree. columns.py:list_column trusts the registry (is_vfs_file) to decide “opens a column”, while api.py:_opens_as_folder asks the provider for real entries — so an empty-provider file (e.g. the CSV stub) is a folder in the server-rendered page and a file with preview over /api/dir. preview.py:render_preview runs a third suffix dispatch, columns.py:entry_icon a fourth (icon table), and render.js’s EDIT_RE edit-gate a fifth. Deletion test: deleting any one copy removes no complexity — each survivor re-derives kind from scratch. These are five shallow modules where one deep module belongs.

Solution

Decide kind once, at the FS seam: every node carries kind ∈ {folder, link, vfs, file} plus a preview hint, set by the three producers (columns.py, api.dir_json, FSA adapter). Consumers — render_preview, entry_icon, EDIT_RE — read the tag instead of switching on the suffix. One Python helper + one JS predicate, pinned by the same test table.

Benefits

Locality: adding .xlsx touches one table, not five switches. Leverage: server HTML, /api/*, and both builds agree by construction — the CSV-stub divergence disappears. Tests: the interface is the test surface: a kind-table test (suffix → kind) covers all five call sites at once.

2. Column order is decided twice, with different rules

STRONG

Files: server/src/filemill/columns.py:94 · server/src/filemill/api.py:58–87 · ui/core/sort.js

Problem

The server-rendered column sorts inline — sorted(iterdir(), key=(not is_dir, name.lower)) — while api.py:dir_json returns raw iterdir() order and leaves ordering to the client’s sort.js metadata sweep. Same folder, two orders, depending on which serving path rendered it. The ordering invariant leaks across the FS seam: understanding “why is this row here” requires holding both rules in your head, and changing one visibly reorders half the app.

Solution

Make ordering a property of the adapter, not of each caller: the HTTP adapter serves entries pre-sorted (one shared Python helper used by both list_column and dir_json), and the client trusts server order for HTTP nodes; sort.js remains the sorter for FSA nodes only. One documented rule (“dirs first, casefold”) with a pinned test table per language.

Benefits

Locality: the rule lives in one helper per language instead of one inline lambda plus one metadata sweep. Leverage: every column in both builds obeys the same order without each call site learning it. Tests: a fixed filename fixture asserts identical order from list_column, /api/dir, and the FSA path.

BEFORE — two rules

columns.py: dirs-first, lower()
api.py: iterdir() order (unsorted)
sort.js: metadata sweep

AFTER — one rule, owned per side

order_entries() (Python, shared)
▼
list_column dir_json sort.js (FSA only)

3. Two full client stacks behind one server

WORTH EXPLORING

Files: server/src/filemill/app.py (44 handlers: /click, /api/*, resource routes) · columns.py (htmx columns + inline prune script) · ui/ (JS app + shell.js, nav.js crumbs)

Problem

app.py serves two clients that implement the same finder: the htmx stack (/click + columns.py, with its own breadcrumb renderer and an inline column-pruning script) and the JS app (/api/* + ui/, with shell.js chrome and nav.js crumbs). Breadcrumb, column pruning, and “folder vs preview” branching exist on both sides — candidates 1–2 are instances of this split. Every behaviour change must be made twice, in two languages, and tested twice.

Solution

Choose the seam that survives: keep /api/* + the JS UI as the one interactive stack, and shrink the htmx stack to first-paint / no-JS document pages (_document_page, _representation_html), deleting list_column’s interactive branches. Or the reverse — but not both.

Benefits

Locality: one place where “clicking a row” is decided. Leverage: candidates 1–2 dissolve rather than being synchronised. This is flagged Worth exploring — not Strong — because it re-litigates a load-bearing choice (offline/embedded pages?) that needs the grilling loop, not a report.

JS app: /api/* + ui/
same finder, twice, two languages

AFTER — one finder + documents

/api/* + ui/ (the finder)
document pages (first paint / no-JS)

4. The VFS provider interface is six parameters wide

SPECULATIVE

Files: server/src/filemill/vfs.py:40–48 · server/src/filemill/columns.py:204–232 (fmt-bar)

Problem

VFSProvider.render_preview(path, vpath, fmt, page, limit, col) asks every provider — and every caller — to understand view mechanics (format toggle, pagination, column index) alongside data access. The interface is nearly as complex as some implementations (csv/json stubs), which is the textbook shallow-module smell: adding a fourth provider means learning six parameters to use two.

Solution

Bundle the view mechanics into one ViewSpec(fmt, page, limit) value object constructed at the route layer: providers take (path, vpath, view). Only pursue alongside real provider pain (a fourth provider, or pagination bugs) — one adapter per future need is hypothetical-seam territory.

Benefits

Depth: smaller interface over the same behaviour. Tests: providers testable with a default-constructed view instead of six-arg scaffolding.

BEFORE

render_preview(path, vpath, fmt, page, limit, col)

AFTER

render_preview(path, vpath, view: ViewSpec)

Top recommendation

Tackle candidate 1 (file-kind) first. It has a demonstrated divergence today (CSV-stub folder-vs-file), not a hypothetical one; it is small (one helper per language + a shared test table); and it is the prerequisite that makes candidate 2 trivially statable (order within a known kind) and candidate 3 decidable (the “folder vs preview” branch is currently the load-bearing overlap between the two stacks). Sequence: 1 → 2 → grill on 3; 4 only with a fourth provider or a pagination bug.
